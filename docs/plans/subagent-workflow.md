# ImageManager2 子 Agent 协作方案

日期：2026-09-18  
状态：已由根目录 `AGENTS.md` 设为项目默认工作流；由主 agent 按任务执行，未安装额外编排服务或修改应用模型配置。

## 1. 目标与原则

由 GPT-6 Astra 主 agent 理解需求、制定可执行方案并负责集成；将边界明确的实施任务交给其他模型；通过独立审核和实际验证控制质量。

当前明确禁用 `gpt-5.6-luna`：不派发任务、不做连通性测试、不将它列入重试或回退链。除非用户后续明确恢复，否则持续遵守这一约束。

角色按任务创建，不要求每个需求都启动完整团队。主 agent 始终负责最终结果，不能把子 agent 的“已完成”直接当作项目验收通过。

本方案基于现有项目目录和本次会话工具所列能力。Terra 的账号可用性尚未验证；模型成本和速度需要实际记录，不承诺固定节省比例。这里的角色是任务分工，不代表应用已经存在同名配置或常驻进程。

## 2. 角色和模型

| 角色 | 默认模型 | 职责与交付 |
| --- | --- | --- |
| 主 agent／架构师／集成人 | `gpt-6-astra` | 理解需求、检查代码、确定契约、划分文件所有权、实施关键部分、集成和最终验收 |
| 界面实施 agent | `gpt-5.6-terra` | 实现约定范围的 Avalonia 视图、绑定、ViewModel 和交互；提交修改清单及验证结果 |
| 服务实施 agent | `gpt-5.6-terra` | 实现约定范围的服务、仓储和数据处理；提交修改清单及验证结果 |
| 独立审核 agent | `gpt-6-astra` | 对照原始需求和最终差异，检查正确性、架构边界、回归与验证缺口 |

初期只使用 Astra 和 Terra，减少模型路由复杂度。不要同时改变模型、任务粒度和验收标准，否则难以判断效果来自哪里。

主 agent 直接负责难以拆分的设计问题以及高风险实现，例如数据库迁移、文件删除、复杂并发、GPU 资源生命周期、跨模块性能问题。常规代码量大不等于适合低成本模型；决定因素是任务边界和判断难度。

独立审核使用新的上下文，输入原始需求、必要契约、代码差异和验证证据。无需复制完整对话，也不以实施者的自评代替检查。

## 3. 何时启用子 agent

| 任务类型 | 执行方式 |
| --- | --- |
| 文案、小布局、单点逻辑修正 | Astra 单独实施和验证 |
| 一个边界明确的独立模块 | Astra 主导，按需要启用一个 Terra 实施 agent |
| 界面和服务可通过稳定接口分开开发 | Astra 确定契约，两个 Terra 实施 agent 并行，完成后独立审核 |
| 高风险或跨层重构 | Astra 实施关键部分，Terra 处理独立常规部分，Astra 独立审核 |
| 原因不明的故障、接口尚不明确 | 主 agent 先定位问题，明确可拆分任务后再派发 |

默认最多两个实施 agent 并行。审核通常在集成后进行，不必同时维持四个活跃角色。如果主 agent 的下一步必须等待某项工作完成，且没有其他独立工作，应优先自行完成该项工作，避免增加交接延迟。

## 4. 项目内的职责边界

本项目采用 .NET 8、Avalonia、MVVM、SQLite 和 ONNX。这里的“前端”是桌面界面，“后端”主要是进程内服务，不默认引入 HTTP API、独立服务进程或其他新架构。

| 代码范围 | 默认负责人 | 分工规则 |
| --- | --- | --- |
| `src/ImageManager.App/Views`、`Controls`、指定 ViewModel | 界面 agent | 负责交互、绑定、显示状态，禁止直接操作数据库 |
| `src/ImageManager.Infrastructure` 中指定服务或仓储 | 服务 agent | 按 Core 契约实现，保持 UI 无关 |
| `src/ImageManager.Core/Models`、`Services` | 主 agent | 先确定数据模型和服务契约；实施者遇到缺口先报告 |
| `src/ImageManager.Common` | 主 agent 分配 | 只在本次任务确实需要时修改，避免扩大公共依赖 |
| `App.axaml.cs`、项目文件、共享资源和公共注册 | 主 agent | 集中处理依赖注入、项目引用和共享接线 |
| `App/Services` 及跨职责文件 | 按具体任务指定 | 先看实际职责，不能仅凭目录名称归属 |

每次派发给出具体文件或小范围目录清单；同一轮一个文件只交给一个实施者。大型 ViewModel 如果需要双方修改，由一方持有文件，另一方提供接口或修改建议，再由主 agent 集成。

上述规则是默认分工，不要求为配合 agent 而重构现有代码。

## 5. 执行流程

### 第一步：确认基线和需求

主 agent 检查相关代码、项目约定和当前未提交修改，记录需要保留的用户改动。列出预期行为、范围、失败情况和验收条件。

已有未提交改动不是自动停止的理由。能安全继续时保留并基于它们工作；重叠变更无法判断意图时再向用户澄清，不覆盖、重置或擅自提交已有修改。

### 第二步：给出最小可执行方案

简单任务在任务说明中记录即可；中大型任务在 `docs/plans/` 记录方案，至少包含：

- 用户可观察到的行为和明确的非目标。
- 相关模块、现有实现和计划修改的文件。
- 公共契约：方法、数据类型、错误处理、取消、进度和线程约定。
- 实施任务依赖、文件所有权和验收条件。
- 高风险点及对应验证方法。

接口确定后再并行。若实施中发现契约有误，实施者报告具体缺口，主 agent 修订并同步受影响任务；不得让双方分别扩展出不一致接口。

### 第三步：派发有界任务

实施 agent 直接修改其分配范围的代码，不只给出伪代码或建议。任务输入只包含必要上下文、契约、参考实现、写入范围和验收条件。

主 agent 同时处理不重叠的工作，例如关键实现、集成接线、验收准备；不重复实施已派出的任务。

### 第四步：收回结果并集成

实施者交付修改文件、行为变化、验证命令与结果、未完成项及已知风险。主 agent 检查范围和接口一致性，将结果纳入统一工作区。

不同执行环境可能共享工作区或使用隔离副本。派发前确认实际机制：共享工作区严格按文件分工；隔离副本必须确认包含所需基线，收回后显式合入并检查。不能假设子 agent 的“完成”意味着代码已经出现在主工作区。

需要隔离时可使用独立 worktree，但不能假设它会自动包含主工作区的未提交改动。主 agent 应确认所需改动如何安全带入，并记录来源。

### 第五步：统一验证与独立审核

在集成后的最终代码上进行构建和相关验证，再向审核 agent 提供同一版本的代码差异与证据。审核 agent 默认只读，不与实施 agent 同时修改代码。

审核关注原始需求、契约、边界条件和实际风险。每个问题应包含位置、触发条件、影响和修复建议，避免把个人风格偏好当作缺陷。

主 agent 判断问题是否成立，交给文件负责人修复或自行处理。修复后执行受影响的检查；重要修复交回审核者确认。只要代码有后续变化，就不能把之前版本的通过结果当作最终版本已验证。

### 第六步：交付

最终报告说明完成的行为、验证证据、未解决限制和需要用户操作的事项。模型不可用、缺少 GPU 或无法执行 UI 验证时如实说明，不将未执行检查写成“通过”。

不因使用子 agent 自动提交、推送、发布或修改用户机器的运行配置；这些动作继续遵循当前任务授权。

## 6. 验证与审核重点

| 变更 | 必要验证重点 |
| --- | --- |
| 普通代码变更 | `dotnet build ImageManager2.sln`，以及受影响的现有检查 |
| Avalonia 界面和 ViewModel | 绑定、命令状态、加载/空/错误状态、窗口关闭和实际操作 |
| 异步任务 | UI 线程更新、取消、重复启动、异常和事件订阅释放 |
| SQLite／仓储 | 数据范围、事务、旧数据兼容、并发读写；使用可丢弃测试数据 |
| 图片／视频／推理 | 资源释放、缺失或损坏输入、内存限制、无 GPU 情况 |
| 性能变更 | 相同数据和环境下的前后对比，避免只凭主观判断 |

针对真实风险添加必要的回归测试，不为简单文案或可逆布局修改制造大量测试。编译成功不能替代交互验证；没有相应环境时交付明确的待验证步骤。

审核的重点是数据丢失、范围错误、竞态、界面卡顿、资源泄漏、行为遗漏和架构依赖倒置。严重问题必须修复，或明确报告为未完成；不能为了完成流水线隐藏问题。

## 7. 模型失败和任务升级

1. Terra 返回权限拒绝、模型不存在等确定性错误：停止该模型派发，由主 Astra 接手，记录原因；不反复重试。
2. 短暂网络错误或超时：先检查任务状态，确认没有仍在运行的实施者，再进行一次合理重试；失败则由 Astra 接手。
3. 任务范围失控、必须更改公共契约、存在关键语义歧义：暂停相关实施，由主 Astra 决策后再继续。
4. 同一问题连续两轮修复仍未解决：升级给主 Astra，不继续消耗在重复反馈上。
5. 独立审核 agent 无法启动：主 agent 执行复核，并在交付中注明未完成独立审核；高风险变更明确保留这一验收缺口。
6. Luna 永不作为本方案的回退选项。若外围审批服务自行配置为 Luna 并报错，这与实施 agent 选型不同；应报告环境阻断，不能声称通过更换子 agent 模型解决，也不能绕过审批。

接手前确认原实施者停止写入或已结束，避免旧任务和主 agent 同时修改文件。无需为每次已约定的 Astra 接手重新询问用户；涉及需求改变或新增高影响操作时另行澄清。

## 8. 可复用任务说明

### 实施任务模板

```text
角色：界面实施 / 服务实施
模型：gpt-5.6-terra；不可用时由主 Astra 接手；禁用 Luna
目标：<用户可观察到的结果>
输入基线：<当前代码版本、必要的未提交修改或已合入契约>
契约：<接口、数据类型、错误/取消/进度语义>
参考：<必须阅读的文件和现有模式>
允许修改：<具体文件或小范围目录>
禁止修改：<公共契约、他人持有文件和无关模块>
验收：<正常路径、关键异常路径及验证方法>
协作：直接实施；保留已有改动；接口缺口先报告；不得自行转派
交付：修改文件、行为说明、实际验证结果、未完成项和风险
```

### 审核任务模板

```text
角色：独立审核，默认只读
模型：gpt-6-astra
输入：原始需求、已确定契约、最终集成差异、验证结果
检查：需求满足、边界条件、架构依赖、数据范围、并发与资源释放
输出：按严重程度列出可复现或有代码证据的问题
每项包含：文件位置、触发条件、实际影响和修复建议
没有发现问题时：说明检查范围与尚未验证的风险，不承诺绝对无缺陷
```

## 9. 项目场景示例

以未来“扩展向量索引任务进度与取消交互”为示例，不代表现在修改该功能：

1. 主 Astra 先核实 `IVectorIndexService` 和现有实现，明确进度、取消完成时点、部分结果保留策略与重复启动行为。
2. 主 Astra 负责必要的 Core 契约调整，分配具体文件。
3. 界面 Terra 持有 `VectorIndexViewModel.cs` 和 `VectorIndexWindow.axaml`，实现展示和命令状态。
4. 服务 Terra 持有 `VectorIndexService.cs` 及明确分配的实现文件，遵循契约上报进度和响应取消。
5. 主 Astra 处理接线和统一验证，独立 Astra 审核取消后重试、关闭窗口、失败恢复和数据范围。

上述文件在编写本方案时已有未提交修改。实际试点前必须重新检查基线，不得用本示例直接覆盖当前工作。

## 10. 落地与评估

第一阶段：根目录 `AGENTS.md` 已引用本方案，新对话读取项目指令后按需采用。选择一个接口清晰的中型功能，由主 agent 按本方案编排子 agent。首次实际派发时验证 Terra 可用性，失败按既定规则接手。

第二阶段：记录多个相近任务的总耗时、可获得的模型用量、返工轮数、集成冲突和审核发现。计入主 agent 的方案、交接、复核时间；缺少计费数据时不估称节省金额。

第三阶段：根据实际效果迭代项目 agent 指令和本方案；确有需要时，再按届时运行环境支持的方式配置额外编排机制。不凭空编写未经核实的配置项。

若并行实施确实降低总耗时，且没有显著增加返工和缺陷，则保留；若瓶颈是接口沟通、重叠文件或隐含需求，则缩小派发范围或恢复 Astra 单独实施。

`.gitignore` 已仅对本方案 `docs/plans/subagent-workflow.md` 开放例外，其他文档继续默认忽略。根目录 `AGENTS.md` 和本方案可一同纳入版本控制；只有实际提交并同步后，其他克隆或从提交创建的 worktree 才能获得这些规则。
